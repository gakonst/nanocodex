# Hand device keys

Every Hand authenticates publication with its own Ed25519 device key. The
private key is generated on the Hand and never leaves it. The key proves only
"enrolled device D of account A" and buys short-lived, Hand-only publication
credentials. It never acts as an account credential or as an SSH key.

## Three identities

| Identity | What it is | What it authorizes | Where it lives |
| --- | --- | --- | --- |
| Device authentication identity | Ed25519 key pair generated by the Hand | Publishing exactly one `machine_id` (tool host, screen and ICE, VM factory) | Private key: Hand state directory. Public key and status: the owner's `AccountHostedTools` Durable Object |
| SSH host identity | The sshd host key of a server | Nothing by itself. It lets the brain recognise the server it connects to | Server `/etc/ssh`. The Vault target pin, and optionally fingerprints attested by the server's active device |
| Outbound client authority | The Vault SSH client key and the account principal used by the brain | Logging in to a server, running commands | Encrypted credential broker in egress. Never exported |

These identities are never derived from each other. A device key is never
offered as SSH client authentication. A host-key attestation never grants
login: the Vault client key stays the only SSH client authority, and the
server's `authorized_keys` still decides access. The bootstrap is always a
user act: the owner saves a Vault SSH target (hostname, port, username, client
key and, for a new server, its pinned host fingerprint) and authorizes its
public key on the server. Device host trust only keeps recognising that server
after its host key changes.

## Enrollment

A computer Hand enrolls on its first start with the existing account login:

1. `POST /v1/account/hand-devices/challenges` returns a stateless MAC'd
   challenge (120 s).
2. The Hand generates its key and sends `POST /v1/account/hand-devices`
   `{machine_id, name, algorithm: "ed25519", public_key, challenge, signature}`.

Account routes need `agents:write` (`agents:read` for listing) and
`tools:use`, and accept only a live account session or account API key.
Connect grants, service principals and device credentials are refused. Writes
from a browser session must be same-origin. The service rejects small-order or
non-canonical public keys, a raw key already used by any device of the
account, machine IDs with the platform prefixes `server:`, `cf:`,
`shared:`, `vm:` and `screen:`, and machines currently published by a
sandbox, server or leased-VM publisher. Repeating an enrollment of the same
active key is idempotent (200). A different key for an active machine returns
409 `hand_device_exists`. The device record keeps `enrolled_by` (principal
kind, organization, team, authorization epoch).

A server Hand cannot hold an account login. `server_hand connect` asks the
owner DO for a one-time grant `ncxhg1.{owner}.{host_id}.{secret}`. The grant
is bound to machine `server:{host_id}`, single use, stored only as a digest,
and expires after 10 minutes. It travels only on stdin of the Vault-pinned SSH
session into the 0600 file `/state/device-grant` in the server container,
never in argv, environment or logs. The publisher then generates its key in
`/state/hand-device/` and enrolls with
`POST /v1/hand-hosts/{owner}/{host_id}/hands/device` (bearer = grant). The
grant is consumed atomically and the file is deleted. A grant enrollment
replaces an earlier device of the same server. No long-lived server bearer is
minted on this path.

## Proof of possession

Device operations start with
`POST /v1/hand-devices/{owner}/{device}/challenges {purpose}`, which returns
a 60 s challenge with the current `key_version` and key fingerprint.
Challenges are MAC'd by a DO secret over purpose, owner, device, key version,
nonce and expiry. A challenge is single use: the signature is verified first,
then the nonce is checked and recorded in the same synchronous storage
transaction that issues the result. A failed signature never burns a valid
challenge, and a replay can never succeed twice.

Signed messages are UTF-8 fields joined by `\n`, domain-separated by
`nanocodex-hand-device:v1`, the purpose and the Worker's public origin:

```text
enroll         domain|enroll|origin|owner|challenge|machine_id|public_key
credential     domain|credential|origin|owner|device|key_version|challenge
rotate         domain|rotate|origin|owner|device|key_version|challenge|new_public_key
ssh-host-keys  domain|ssh-host-keys|origin|owner|device|key_version|challenge|sorted fingerprints
```

A signature for one account, origin, device, key version or purpose
therefore verifies for no other.

## Device credentials and renewal

`POST /v1/hand-devices/{owner}/{device}/credentials` returns
`ncxhd1.{owner}.{device}.{secret}`. Only the SHA-256 of the secret is stored.
A credential lasts 15 minutes by default
(`NANOCODEX_HAND_DEVICE_CREDENTIAL_TTL_SECONDS`, clamped to 5–900). At most
four are outstanding per device. Issuance re-checks live account authorization.
Every use re-reads the device: active, current key version, unexpired.

The credential is a fixed Hand-only scope. It is accepted only by
`/v1/account/tool-host`, `/v1/account/hands/{host,ice,renew}`,
`/v1/account/vm-host` and the server publisher routes
`/v1/hand-hosts/{owner}/{host_id}/hands/{host,ice,renew}`. Every other route,
and account `authenticate()`, rejects it. Requests are forwarded with only
the credential and the machine/runtime headers, never account capability
headers. The tool host requires `x-nanocodex-hand-machine-id` to equal the
device's machine. Screen publication is scoped to
`{machineId, routeId: "hand-device:{id}", expiresAt}`. A VM factory is
bound to its device's machine. Sockets carry a `hand-device:{id}` tag that
survives hibernation, and the device row is re-checked synchronously
immediately before `acceptWebSocket`.

A tool-host socket outlives individual credentials. Screen publishers renew by
presenting a newer valid credential to `hands/renew`, which extends the
publication scope to that credential's expiry. The Hand fetches a fresh
credential before every connect, reconnect and renewal.

## Rotation

`nanocodex hand devices rotate` writes `device-key.v1.pending` durably before
calling `POST /v1/hand-devices/{owner}/{device}/rotate`, signed by both the old
and new key over the same message. On success the key version increments,
old-version credentials stop working at once, live tool-host, screen and VM
factory connections of the device close, the device's SSH host attestation is
cleared, and the pending key is promoted by atomic rename. Each later challenge
reports the service's current fingerprint, so a lost response or crash
promotes the pending key only when the service proves it accepted it. The Hand
re-attests SSH host keys after any rotation.

## Revocation, forget and the downgrade fence

`DELETE /v1/account/hand-devices/{id}` (or `nanocodex hand devices revoke`)
marks the device revoked, deletes its credentials and records its machine as
device-bound in one storage transaction. It then closes the device's tool-host
sockets, fences its screen publishers and VM factory, and reports
`closed_connections`. Revocation is idempotent. Device routes for a revoked or
unknown device answer 401 `hand_reenroll_required`, and the Hand stops with
an actionable error instead of falling back to the account key. Disconnecting
a server (`server_hand disconnect`) or a failed setup deletes the host
record, which also revokes the server's active device and any unused grant.

Once a machine has any device record, the mark is permanent. Account-key
publishers for that machine are rejected with 403 `hand_device_required` at
connect and at catalog admission, including header-less catalogs, hands remote
claims and VM factories. Server bearers are rejected for a server that has a
device. `DELETE /v1/account/hands/{machine}` (forget) revokes active devices
and closes their sockets, but never clears the mark. Re-enrollment through the
account route is allowed; legacy publication is not. The account policy
`PUT /v1/account/hand-devices/policy {require_device_keys}` rejects every
account-key publisher when true. Any `agents:write` + `tools:use` principal
may enable it. Disabling it requires a signed-in browser session. The policy
covers account-key publishers only: tool hosts, hands remote claims and VM
factories authenticated with an account key. Platform-scoped publishers
(server `hand-host` bearers, `cf:` sandbox publishers and leased-VM
publishers) do not authenticate with an account key and cannot enroll a
device (their machine prefixes are reserved), so `require_device_keys` does
not apply to them. A server's `hand-host` bearer is refused only once that
server itself has an enrolled device.

Legacy account-key publication remains only for an install that never
enrolled, against a service whose enrollment route is absent (the route marker
header `x-nanocodex-hand-devices: v1` distinguishes route errors from a
missing route). Each legacy connection is logged as
`{type: "hand.connection", auth_mode: "account_api_key", legacy: true}` and
listed under `legacy` by `GET /v1/account/hand-devices`. Once `device.json`
exists the Hand never publishes with the account key again.

## Key storage on the Hand

The Hand state directory is 0700 and owned by the Hand's user. It contains
`device-key.v1` (PKCS#8 Ed25519, 0600, created with
`O_CREAT|O_EXCL|O_NOFOLLOW` and fsynced), `device-key.v1.pending` during
rotation, non-secret `device.json` (owner, device, machine, key version,
fingerprint, origin) and `device.lock`. Every load checks file type, owner and
mode and refuses symbolic links. The lock serializes first run, credential
issuance, attestation and rotation across the daemon and CLI. Secrets are
zeroized and redacted from `Debug`, logs, `--describe` and child
processes. A server container keeps the same files in `/state/hand-device/`.

Platform coverage: the key is a 0600 PKCS#8 file on every platform. macOS
Keychain, Windows TPM/CNG and Linux TPM storage are not used, so a process
running as the Hand's user (or root) can read the key; revocation is the
response to that compromise. On Windows the file lives in the per-user profile
but the POSIX owner and mode checks do not apply. ring's in-memory key pair and
its generated PKCS#8 document cannot be zeroized; only the Hand's own copies
are wrapped in zeroizing buffers.

`nanocodex hand devices list|revoke|rotate|reenroll` manages devices;
`reenroll` discards the local enrollment so the next start enrolls a new
device.

## SSH host attestation and recovery trust

An enrolled Hand attests its sshd host public keys with
`PUT /v1/hand-devices/{owner}/{device}/ssh-host-keys`
`{challenge, signature, fingerprints}` (at most eight
`SHA256:` + 43 base64 characters). It reads
`$NANOCODEX_HAND_SSH_HOST_KEY_DIR/ssh_host_{ed25519,ecdsa,rsa}_key.pub`
(default `/etc/ssh`) at every start, after rotation and every 10 minutes while
publishing, and sends the set when it changed. A server Hand therefore
re-attests a rotated sshd host key when its container restarts, or within 10
minutes while its screen is published. A server container receives only the
host's public key files, bind-mounted read-only one file at a time at
`/ssh-host-keys`; private host keys are never visible to it. The attestation
is stored with the device, with its time, and describes only that device's own
machine.

A Vault SSH target has a host authority: a pinned `host_key_sha256`, an
owner-saved `host_key_trust` binding, or both. A binding is `device` (the
reference's own server Hand, machine `server:{serverHandID(owner, ref)}`) or
`hand:MACHINE_ID` (one exact enrolled Hand, for example a computer reached
over SSH). A target with neither is rejected; there is no trust on first use.
Targets are immutable: changing the hostname, port, username, pin or binding
means deleting and re-creating it, and the credential broker stamps
`saved_at` on every creation.

Device trust applies to a call when the caller opts in or the target has a
saved binding. The shell opt-in is `ssh -o IdentityRef=REF -o
HostKeyTrust=device`; `server_hand` always opts in. The `ssh.internal`
request body may carry only `host_key_trust: "device"`: any other field,
including a host fingerprint, is 400 `invalid_ssh_request`. Egress resolves
the owner from the agent subject and the target from that owner's credential
broker, then asks the managed `HandDeviceSshHostKeys` entrypoint (private
service binding `HAND_DEVICE_SSH_HOST_KEYS`) for the bound machine. The
entrypoint reads `AccountHostedTools.deviceSshHostKeys(owner, machine)` at
call time, without a cache: the ACTIVE device of that machine with its
`created_at` and attested keys, or nothing.

The presented host key is accepted when it matches:

- the Vault pin, if the target has one; or
- with device trust, a fingerprint the bound machine's active device attested
  after the target's `saved_at`. For a `device` binding the device must
  also have been enrolled after `saved_at`, that is, bootstrapped through
  this exact target snapshot.

The decision is made before any socket opens. Without device trust an unpinned
target fails with 403 `ssh_host_key_trust_required`; with device trust and
nothing acceptable it fails with 403 `ssh_host_key_unattested`; an
unavailable attestation source is 503 `ssh_host_key_attestation_unavailable`.
A presented key outside the accepted set aborts the handshake before user
authentication and the command returns exit 255 with
`ssh: server host-key authentication failed`. Revoked or forgotten devices,
other machines' devices, attestations older than the target and attestations
cleared by rotation are never accepted. The egress audit record carries only
`host_key_trust_mode` (`vault_pin` or `device`), the number of attested
keys, the matched `host_key_source` (`vault_pin` or `device:{id}`) and the
public `host_key_sha256`.

The first bootstrap of a server still requires a Vault-pinned host key. A
`device` binding accepts only a device enrolled after the target's
`saved_at`, and before `server_hand connect` no such device exists, so an
unpinned device-trust target fails with 403 `ssh_host_key_unattested`: there
is no trust on first use. `server_hand connect` therefore delivers the grant
over the pinned connection. After the server's device has enrolled and
attested, rotating the server's sshd host key keeps `server_hand` and
`ssh -o IdentityRef=REF -o HostKeyTrust=device` working without editing the
Vault; the pin stays accepted alongside the attestation.

## Threat model

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| Stolen device credential (`ncxhd1`) | Hand-only routes, fixed machine binding, digest storage, 15 min lifetime, re-check of device status and key version on every use, revoke deletes credentials and closes sockets | Until expiry or revocation the thief can publish as that one machine and receive its tool calls |
| Stolen device key, before revocation | Key never leaves the Hand; files 0600 in a 0700 owner-only directory; the key buys only the device's own Hand scope | The thief can impersonate that Hand until the owner revokes it; listing shows the fingerprint and last authentication |
| Stolen device key, after revocation or rotation | Revoked devices get 401 `hand_reenroll_required`; rotation invalidates the old key and its credentials immediately; machine stays device-bound | None for publication; a revoked machine must re-enroll through the account route |
| Replay of a challenge or signature | MAC'd challenges with 60/120 s expiry bound to purpose, owner, device and key version; atomic single-use record after verification | None within the protocol |
| Cross-account use | Keys, devices and credentials live only in the owner's DO; signed messages include the owner; raw keys are unique per account; the DO checks ownership before creating state | A key copied into another account must be enrolled there by that account's own principal |
| Cross-origin use | Signed messages include the Worker's public origin; browser writes require same origin | A signature is valid for the origin it was made for; the origin must be the configured public origin |
| Compromised account key | Device credentials are never account credentials; account keys cannot relax `require_device_keys`; enrolled machines refuse account-key publishers; enrollment notifies via listing | The attacker can enroll new, unreserved machines and revoke devices; server machines need a server_hand grant, which needs full account tool authority |
| Malicious Hand asserting host keys for another server | Attestations describe only the attesting device's machine; recovery looks up the machine bound to the exact Vault reference or saved `hand:` binding, never a hostname; callers cannot supply fingerprints; pin always accepted | A compromised server device can attest arbitrary keys for its own server, enabling a man in the middle for that server only if the attacker also controls the network path |
| Re-pointed or re-created Vault target | `saved_at` snapshot: earlier attestations and devices enrolled earlier never authenticate the new target | A saved `hand:` binding deliberately trusts that Hand's current attestations |
| Local key theft by another user | Owner-only directory and files, owner and mode checked on load, symlinks refused, `O_EXCL` creation, process lock | Root or the Hand's own user on that machine can read the key |
| Legacy downgrade | Permanent device-required mark per machine, checked at connect and catalog admission; optional account-wide `require_device_keys`; Hands never fall back after enrollment | Never-enrolled machines keep account-key publication until the policy is enabled |

## Validation

- `pnpm --filter nanocodex-managed-service run test:hand-device-keys` runs
  the public HTTP/WebSocket journey for enrollment, credentials, replay,
  cross-account and revocation, rotation, the downgrade fence and server grant
  enrollment, with evidence under ignored `output/hand-device-keys/`.
- `NANOCODEX_EVIDENCE_DIR=output/hand-device-keys/ssh pnpm --filter
  nanocodex-egress-service run test:ssh-device-trust` runs the production
  egress Worker, credential broker and `HandDeviceSshHostKeys` entrypoint in
  workerd against a real OpenSSH sshd whose host key rotates. It covers
  pin-only bootstrap, rejected client fingerprints, recovery through the bound
  device's attestation, and refusal for other machines, revoked devices,
  stale or pre-snapshot attestations, re-created targets and unpinned targets
  without attestation. Only the target's DNS answer and the account DO's
  `deviceSshHostKeys` answers are fixtures. It writes
  `ssh-device-trust-trace.json` and the SSH audit log.
- `NANOCODEX_HAND_EXECUTABLE=target/debug/nanocodex-hand pnpm --filter
  nanocodex-managed-service run test:hand-device-server-hand` chains the
  whole server path without fixtures for the account DO: the managed and
  egress Workers run together in workerd against a real OpenSSH sshd. An
  unpinned target cannot bootstrap; the owner DO mints the grant; the shipped
  `SERVER_HAND_INSTALL` script receives it over Vault-pinned SSH; the shipped
  `nanocodex-hand server-host` publisher enrolls, deletes the grant and
  attests the host key; a replayed grant is 401; after the sshd host key
  rotates and the container restarts, recovery succeeds through
  `device:{id}` without editing the Vault; after revocation it fails closed
  and the publisher stops. Docker and the desktop compositor are stand-ins
  (`js/managed/test/support/server-hand/`), so the screen itself is not
  published. Evidence goes to `output/hand-device-keys/server-hand-journey/`.

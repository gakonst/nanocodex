# Claude-native tool implementation matrix (2026-09-29)

See [runtime context, cache and recovery behavior](CLAUDE_RUNTIME.md) for current semantics. Older dated probe sections below record observations from their respective builds.

The Claude backend must **never advertise** `exec_command`, `apply_patch`, `web__run`, `exec`, `wait`, or Responses `tool_search` to Claude. `nanocodex-claude-tools` independently supplies Claude-native adapters behind explicit host capabilities and permission policy. The former `nanocodex-tools` OpenAI runtime is now `nanocodex-oai-tools`; Claude does not depend on it or import its definitions. A tool is only advertised when its implementation, permission boundary and result encoder are available. This inventory tracks the current Claude Code tools reference, not a promise that every item is present in every CLI session/provider/platform.

| User-defined functions | caller-provided Claude `ToolDefinition` | **Implemented** with assistant `tool_use` and single user `tool_result` message, ordered error results, session-level replay-ID rejection, and cancellation admission checks. `tool_with_context` supplies stable session/turn/call identity. With the shared durability adapter, committed model/tool effects and terminal requests replay after reopen; unfinished effects remain at-least-once. Optional parallel execution requires caller to attest independence; attached durable task boards force sequential tool execution. No Codex definitions are implicitly loaded. |

Safety design: Claude-visible registry and JSON schemas are independently versioned; translate into a private executor with `(session, turn, tool_use_id)` effect receipts, host approval and filesystem/network boundaries. The Claude tools crate has no ambient runtime or shell: the caller must install and authorize each capability; the OpenAI workspace runtime is not part of this boundary. Limit result bytes/media and preserve source citations. Committed cancellation/unknown-outcome receipts replay without invoking the handler. Unfinished effects lacking a committed receipt follow the shared durability store's at-least-once policy; external hosts must deduplicate or reconcile with stable call identity. Keep same-tool result blocks together, signed thinking and server result ciphertext unmodified. Native server tools are charged separately; opt-in only. No real subscription token or provider traffic was used in the synthetic tests.

## Default local setup

The Rust facade's `Backend::claude(api_key)` and Node's
`Backend.claude({ apiKey })` assemble their supported local tool catalogs.
Callers choose the backend and workspace; individual tool registration is an
advanced customization path. See the [Rust guide](../crates/nanocodex/README.md)
and [JavaScript guide](CLAUDE_JAVASCRIPT.md) for the tools installed on each host.
The coverage limits in the matrix still apply.

## Runtime integration boundary

The same `.durability(state).await?.build()?` extension now attaches Claude to `nanocodex-durability` (`claude` feature), including its stores, admission, owner fencing and effect receipts. SQLite reopen and transaction-fault tests cover frozen unfinished requests, completed model/tool replay, signed/opaque compaction context, discovery/container recovery, durable task state and interruption notices that survive lossy summaries. An effect without a committed receipt can still execute again after a crash. Snapshots are whole provider-native JSON payloads, without paged transcript storage optimization.

Rust Claude/durability compilation for `wasm32-unknown-unknown` is verified. The [JavaScript API](CLAUDE_JAVASCRIPT.md) exposes the Claude WASM runtime and shared store contract. The Node backend constructor supplies local handlers automatically; the low-level constructor accepts explicit handlers. Neither installs Codex tool definitions into Claude. Managed provider selection, product sign-in and complete host services remain separate work. Synthetic WASM execution evidence is distinct from live provider evidence. The native subscription manager implements the login/refresh protocol observed in Claude Code 2.1.283 over private host storage and HTTP. Synthetic SQLite integration covers its composition with agent execution; live independent native admission was verified with the observed compatibility profile, including tools, cache hits, compaction and recall after SQLite reopen. Fresh native PKCE authorization/refresh and product sign-in remain unverified. See [runtime coverage and limits](CLAUDE_RUNTIME.md) and [authentication](claude-authentication.md). The adapters and tests do not establish full Claude Code parity.

## Controlled 2.1.284 CLI wire checks (fake-key loopback, no subscription traffic)

A non-bare interactive invocation exposed `AskUserQuestion`, `EnterPlanMode`, and `ExitPlanMode` in addition to the 20 tools of default `-p`; a forced-all `-p` fixture exposed 26. These sets are conditional, not a universal full registry. A non-first-party `ANTHROPIC_BASE_URL` disables tool search by default per the [official environment reference](https://code.claude.com/docs/en/env-vars). With `ENABLE_TOOL_SEARCH=true`, a print request instead exposed `ToolSearch` and `DeferredToolPlaceholder` among 12 initial tools. A synthetic `ToolSearch` call selected `WebSearch`; the next request advertised `WebSearch` and returned a user `tool_result` containing a `tool_reference`. This is a Claude Code **client** discovery flow, distinct from Anthropic's server tool-search API. At least 31 unique names were observed across these fixtures; that is not an exhaustive count.

With a synthetic long first assistant response, `--continue` performed a separate, ordinary Messages summarization request containing prior history and a text-only compaction instruction, then rebuilt the next request around the returned summary. It continued to advertise its three bare-mode tools even on the summarization request; no top-level API `compaction` parameter or `compact_20260112` edit appeared. A separate two-`Read` call test returned both matching results in one user message with the failed result marked `is_error:true`; result blocks arrived in completion order, not necessarily tool-use order. These are controlled wire observations, not evidence about live subscription billing or real-model decisions.

## Authenticated 2.1.284 subscription sample (synthetic prompts)

A process-local, credential-redacting TLS relay of the **actual logged-in CLI** (not a fake API-key fixture) measured 20 successful `-p` prompts plus a separate valid three-turn continuation and four long-context turns. No credential/header values or full content were retained. Real main requests used four system blocks with 1-hour ephemeral cache markers, adaptive thinking with `display:updates`, and `diagnostics.previous_message_id`; the earlier fake-key fixture's three-block system and `display:omitted` must not be treated as subscription parity. Subscription authentication was handled entirely by the installed CLI, not this backend.

Claude Code's `WebSearch` is a **client** tool, but servicing it triggered a **nested streamed Messages request** with Anthropic's `web_search_20250305` **server** tool. The CLI then fed the nested search's outcome back as a string user `tool_result` for its original client call. A deferred `ToolSearch` call exposed `WebSearch` in the next main request; two discovery workflows each called web search twice. The opt-in `.nested_web_search()` now exercises the two-layer path in a synthetic test; `ClaudeWeb` remains an independently injected provider adapter.

Two actual client-managed compactions were observed with `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` and unusually long synthetic inputs. Each made an ordinary Messages request marked by the CLI's `x-claude-code-request-class: compaction`, carrying prior history and a text-only summary instruction; the same client tools remained advertised. The next `main` request used a continuation preamble and summary. Neither API `compaction` nor `compact_20260112` was sent. These observations do not establish default trigger frequency or confer authority to copy first-party identification headers into Nanoclaude; subscription transport requires its own approved integration.

## Actual interactive 2.1.284 TTY correction

A new tmux-driven authenticated CLI trace is summarized in [the interactive report](research/nanoclaude-interactive-tty.md). The initial interactive catalog was 13 tools (Agent, AskUserQuestion, Bash, Edit, ListAgents, Read, ReportFindings, ScheduleWakeup, Skill, ToolSearch, Workflow, DeferredToolPlaceholder, Write), rather than a universal print-mode set. WebSearch, WebFetch, ExitPlanMode were loaded conditionally; `select:Glob` returned no matching tool in this session. Actual client WebSearch used auxiliary `web_search_20250305` with `tool_choice:auto`; WebFetch fetched an allowlisted public URL directly and summarized it with auxiliary Haiku 4.5. AskUserQuestion, manual Edit approval and plan execution approval required native terminal UI. Agent spawned a separate six-tool subagent and asynchronous handback. Tool schemas/availability must be based on the selected interactive mode and capabilities. The new nested WebSearch and injected-source WebFetch paths cover only synthetic wire layers, not the complete harness.

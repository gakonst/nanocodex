# Longer discovery caching and connection retention

User steering: stable metadata should be cached substantially longer instead of repeatedly rechecked and repulled. The follow-up separates discovery freshness from the 120-second signed-access lifetime.

The discovery policy is a 15-minute, bounded, binding-and-authority-scoped in-memory snapshot shared opportunistically across Session instances in the same isolate. Catalog and safe Vault reference metadata share one original expiration. Hits do not extend it; an outer projected-account cache must not give an aged catalog another full TTL. Each use projects the current turn's connector/connection authorization. Failed discovery does not become a successful long-lived empty cache. Explicit environment/runtime inspection invalidates the snapshot and loads fresh metadata; lifecycle/configuration invalidation and authority-key changes also prevent reuse. Cross-isolate reuse is not guaranteed; no additional cache service or network round trip is introduced.

Live hand inventory retains its existing shorter refresh window. Provider credential resolution, signed-access validity, per-tool authorization and broker refresh/revocation behavior are unchanged. Metadata can remain stale within its TTL after an external account change until explicit refresh; it never grants permission to execute a disconnected or unauthorized tool.

Production idle runtime retention increases from 30 seconds to five minutes, still bounded by the existing configuration clamp. The development configuration keeps its one-second setting; discovery lifecycle tests explicitly use a 30-second teardown, and a separate test exercises five-minute retention. This preserves the already-owned provider connection through normal pauses; after expiry, ordinary runtime teardown and fresh connection-time credential resolution still apply. It increases the time an idle runtime and established socket remain resident. This does not add a new credential cache or change existing socket revocation semantics.

Prior measured idle reconnect was 676–725 ms after a 36-second pause. Removing that reconnect is the expected structural effect, not yet a measured post-deployment result. Compare connection counts and server admission/handshake phases as well as client TTFT. New client measurements must record host load because the earlier Mac cohort ran under severe load.

Validation: 53/53 shared-discovery, catalog and account-info tests pass, plus 39/39 startup/lifecycle tests and managed typecheck. Cases cover cross-instance coalescing, independent catalog completion, lazy Vault reads, a single original expiry even for a late Vault load, authority/binding isolation, 64-entry eviction, failed/malformed metadata, cancellation isolation, explicit invalidation, stale-result races and per-call authorization projections. The five-minute lifecycle test proves a 36-second return uses the same socket and that a later idle expiry closes it while retaining valid discovery. The initial lifecycle run exposed two fixtures that implicitly depended on the old production timeout; those fixtures now set 30 seconds explicitly, while the retention case sets five minutes. Receipts: `output/inference-discovery-runtime.*`, `output/inference-discovery-types.*`, `output/inference-cache-lifecycle-final.*`.

Cache records include the admission trace ID, hit/miss state, age and remaining TTL; they exclude owner identities, cache keys and metadata contents. Actual catalog and Vault fetch timing remains separate, so an in-flight coalesced hit is distinguishable from avoiding all discovery work. Logs cannot fail admission.
